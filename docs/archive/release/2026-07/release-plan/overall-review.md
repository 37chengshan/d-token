# d-token 发布实施计划总审查

## 1. 审查结论

本计划总体符合最新 PRD 方向：第一版不再按内部 demo 或开发测试面板推进，而是以可公开试用的稳定 Beta / 候选发布版为目标。计划将产品信息架构、真实连接闭环、智能学习、可观测与回退、UI 稳定性拆成 5 个阶段，顺序合理，边界清晰。

最关键的产品决策已经覆盖：

1. 页面结构从工程页重构为 5 个主页面 + 设置。
2. 第二页成为安装与连接工作台，包含一键安装、智能学习、高级安装、日志。
3. 第三方工具只检测，不自动安装。
4. cc-switch 默认只读，但必须支持当前 profile/config/upstream 读取和上游自动同步。
5. 第一版重点验收 Claude Code、Codex、OpenCode、Cursor、Cline、CommandCode。
6. 智能学习必须全面扫描、快速准确排序。
7. 智能学习可以直接写入，但只能插入或追加 d-token 管理内容块。
8. Doctor 低风险可自动修复，高风险必须确认。
9. 所有真实写入必须可备份、可回退、可审计。
10. UI 和文案必须从工程语言转为用户任务语言。

## 2. PRD 一致性审查

### 通过项

Phase 1 对齐 PRD 的信息架构要求，解决“页面太工程化、英文太多、用户不知道下一步”的问题。

Phase 2 对齐 PRD 的安装与连接工作台要求，特别强化了 cc-switch 只读读取和上游自动同步，这是当前最重要的真实可用能力之一。

Phase 3 对齐 PRD 的智能学习要求，保留全面扫描和直接写入，同时增加受控写入块、敏感排除、备份回退，避免破坏用户文档。

Phase 4 对齐 PRD 的分析、Doctor、日志、回退要求，保证真实能力可观测、可修复、可信任。

Phase 5 对齐 PRD 的发布标准，强调 UI 完整、稳定性、跨平台、文档和安全验收。

### 需要继续补充的 PRD 细节

1. CommandCode 的实现资料仍不完整：命令名、配置路径、hook 能力、上游配置格式、验证方式都需要补齐。
2. 每个 Agent 的具体配置文件路径和写入策略需要形成独立矩阵。
3. cc-switch 配置格式需要进一步研究，尤其是 profile 切换检测机制。
4. 智能学习全局文档路径需要按 Agent 分别定义。
5. 智能学习扫描算法需要进一步落成数据结构和评分公式。

## 3. 风险审查

### 产品风险

最大产品风险是“功能看起来很多，但用户无法形成闭环”。解决方式是每个功能都必须满足：检测、计划、执行、验证、日志、回退。

第二个产品风险是“UI 仍然像开发工具”。Phase 1 和 Phase 5 必须严格清理开发期语言，不允许 benchmark、fixture、smoke test、payload 等主文案出现在正式 UI。

### 技术风险

Agent 差异是主要技术风险。Claude Code、Codex、OpenCode、Cursor、Cline、CommandCode 的配置位置、hook 机制、上游设置方式可能完全不同，必须建立统一抽象，但实现上逐个适配。

cc-switch 自动同步是高风险高价值点。需要判断采用文件监听、进程状态读取、配置轮询、显式刷新，还是组合策略。

智能学习全面扫描可能带来性能压力。必须采用轻量索引、分批扫描、缓存、进度事件、可停止任务，避免 UI 卡死。

### 安全风险

高风险点包括读取用户配置、读取 Agent 会话、生成日志、导出文件、委托 Claude/Codex、写入全局文档。必须默认脱敏、默认本地处理、默认排除敏感文件，所有写入可回退。

### 发布风险

如果没有真实链路验收，只靠 UI 截图或浏览器预览，发布质量不可信。必须至少完成一个真实 Agent 的完整闭环验收，并逐步覆盖重点 Agent。

## 4. 遗漏审查

当前计划仍需在后续实现前补充以下资料：

1. Agent 支持矩阵：每个 Agent 的检测方式、配置路径、可写字段、验证方式。
2. cc-switch 配置格式研究：目录、文件格式、profile 切换机制、端口来源、上游字段。
3. 文档写入路径矩阵：项目级和全局级 `CLAUDE.md`、`AGENTS.md`、`GEMINI.md`、CommandCode 文档路径。
4. 智能学习评分模型：字段、权重、阈值、排序解释文案。
5. 日志字段规范：哪些字段可存、哪些字段必须脱敏、哪些字段禁止落盘。
6. 回退点数据结构：配置回退、文档回退、Doctor 修复回退需要统一格式。
7. 发布测试脚本：前端 build、后端测试、桌面手工验收、真实 Agent 验收、安全脱敏验收。

## 5. 发布门槛审查

发布前必须满足以下硬门槛：

1. 所有主页面 UI 完整。
2. 所有中文文案清晰友好。
3. d-token 自有本地服务可安装、启动、停止、检测。
4. 第三方工具只检测，不自动安装。
5. cc-switch 配置可只读读取。
6. cc-switch profile 切换后 d-token 上游可同步。
7. 至少一个重点 Agent 完成真实配置闭环。
8. 智能学习可全面扫描并快速排序。
9. 智能学习可直接写入 d-token 管理块，且不改动其他内容。
10. Doctor 可检测已知问题并修复低风险问题。
11. 所有写入都有备份和回退。
12. 日志和导出默认脱敏。
13. 示例数据与真实数据明确区分。
14. Windows/macOS 核心流程通过。
15. README 和用户说明能指导新用户完成安装、连接、验证和回退。

## 6. 总体建议

建议严格按 Phase 1 到 Phase 5 顺序推进，不要先跳到智能学习或高级功能。原因是页面信息架构和真实连接闭环是地基；如果这两部分不稳，后续智能学习、Doctor 和分析页都会反复返工。

最优先落地的三件事：

1. 把 UI 导航和第二页四个上栏做出来。
2. 把 d-token 服务 + Agent 检测 + cc-switch 只读读取 + 上游同步做成真实闭环。
3. 把智能学习的“全面扫描 + 受控写入块 + 回退”做成可验证能力。

完成这三件事后，d-token 才真正从“有能力的工程项目”变成“可发布的本地桌面产品”。
