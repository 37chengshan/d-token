# 产品定位与用户旅程设计

## 1. AiMaMi 的产品本质

AiMaMi 不是单纯的 Codex 配置编辑器，也不是一个只显示额度的 Dashboard。它把 Codex 使用过程中分散在文件、终端、网页和系统进程里的工作收拢为桌面应用，核心价值是“减少上下文切换”。

其典型用户问题包括：

- 当前使用哪个账号，额度还剩多少，何时刷新。
- 当前请求走官方、第三方中转还是本地代理。
- 哪些模型可用，某个 Provider 的状态是否正常。
- 历史会话、配置、MCP、Skills 和自定义指令如何统一管理。
- 代理或 Codex 进程异常时如何快速恢复。
- 应用如何常驻托盘、自动更新并保持单实例。

这类应用的关键并不是“功能多”，而是把高频动作变成连续路径。

## 2. 典型用户旅程

### 2.1 首次启动

推荐流程：

1. 识别 Codex 是否安装。
2. 检查本地配置目录和版本。
3. 仅读取非敏感元数据，列出账号、Provider、模型与 MCP 情况。
4. 展示风险说明，不在首次启动时直接改写用户文件。
5. 让用户选择是否启用托盘、自动更新、启动时运行和快捷键。
6. 进入“今日状态”页面，而不是先展示复杂设置。

### 2.2 日常使用

首页应回答四个问题：

- 当前是否可用。
- 当前走哪条链路。
- 当前额度和使用趋势如何。
- 是否存在需要用户处理的异常。

用户不应该先理解 Repository、Proxy、Route Profile 或 Capability Snapshot 才能使用应用。复杂概念应在高级视图中展开。

### 2.3 修改路由或配置

成熟流程不应只是“修改并保存”，而应是：

```text
扫描当前状态
→ 生成变更计划
→ 展示人类可读摘要
→ 展示精确 diff
→ 创建备份
→ 用户明确确认
→ 原子应用
→ 语义验证
→ 运行 Doctor
→ 生成回退点
```

AiMaMi 提供了完整的任务入口；d-token 在事务模型上更严格。d-token 应把这种严格模型包装成更自然的用户旅程，而不是暴露底层步骤让用户自己组合。

### 2.4 异常处理

建议采用三层恢复：

1. **轻量恢复**：刷新状态、重新检测进程、重新加载配置。
2. **受控修复**：重新应用已审查计划、修复权限、重新建立本地服务。
3. **精确回退**：按 rollback id 恢复原始字节、权限和存在性。

页面应明确区分“系统异常”“配置异常”“Provider 异常”“路由歧义”和“证据不可用”，不能统一显示为连接失败。

## 3. d-token 应如何重新组织用户旅程

当前 d-token 的六个一级页面方向正确，但页面语言仍偏控制面。推荐使用“任务层 + 证据层”双层结构。

### 3.1 一级任务层

- **总体概览**：今天是否正常、请求是否经过 d-token、节省与风险是否有证据。
- **连接工作台**：选择 Agent、选择上游、预览变更、应用并验证。
- **分析**：请求趋势、路由、压缩和失败原因。
- **Doctor**：自动检查、明确问题、可执行修复。
- **变更与回退**：所有真实写操作和 rollback point。
- **设置**：主题、语言、数据保留、更新、系统集成和高级策略。

### 3.2 证据层

每个关键结论都应能展开查看：

- source：来自 Tauri、本地 runtime、Event Ledger 还是 browser preview。
- freshness：何时采集，是否过期。
- state：verified、partial、stale、unavailable。
- action result：最近一次操作是否成功，是否已验证。
- provenance：对应 runtime、route、config revision 和 commit。

这样既保留 d-token 的严谨性，又避免首页堆满工程术语。

## 4. 产品边界

### 4.1 d-token 应做

- 让多个 AI coding Agent 安全接入同一本地控制面。
- 压缩与优化上下文，但对有损能力设置严格证据门槛。
- 明确路由和协议转换，不静默 fallback。
- 记录脱敏的请求、路由、事务和 Doctor 证据。
- 对 Agent 配置进行受控修改和精确回退。
- 提供 Windows/macOS 一致的桌面体验。

### 4.2 d-token 不应做

- 变成账号买卖、账号池运营或批量注册工具。
- 直接接管所有第三方工具的账号生命周期。
- 为了“自动化”跳过 diff、确认、备份或验证。
- 把第三方配置文件内部结构当作稳定公共 API。
- 把估算节省、shadow 结果或 browser preview 宣称为真实运行结果。
- 复制 AiMaMi 品牌、图标、角色、声音或商标资产。

## 5. 产品成功指标

建议分为四组。

### 5.1 激活

- 首次启动到完成首个 verified route 的时间。
- 首次连接过程中需要手工打开终端或编辑文件的次数。
- 首次连接失败后能够自动解释的比例。

### 5.2 可靠性

- 配置 apply 后 verify 成功率。
- 自动恢复成功率。
- 路由歧义被阻止的次数。
- 非 d-token 进程误杀次数，目标必须为零。

### 5.3 用户价值

- 有证据的输入 token 节省。
- 成功 routed 请求数。
- 用户从 Doctor 发现到解决问题的时间。
- 每周使用连接工作台、分析和回退功能的活跃用户比例。

### 5.4 信任

- 页面中 verified/partial/stale/unavailable 状态是否准确。
- 导出和日志中 secret 泄露数量，目标必须为零。
- 回退是否恢复精确原始字节和权限。
- 用户取消操作后是否无任何隐式写入。

## 6. 产品开发方法

1. 先定义用户任务和失败语义，再设计页面。
2. 每个页面必须绑定真实数据来源，禁止先做漂亮 fixture 再假定后端会补齐。
3. 每项写能力必须先定义 transaction contract。
4. 对外文案区分“实现存在”“已验证”“可发布”。
5. 每个新 Agent 接入必须通过相同 adapter 合同和验收矩阵。
6. 先完成一个 Agent 的端到端黄金路径，再扩展矩阵。
7. 系统能力按最小权限逐项开启，不能为了方便一次性放宽 Tauri capability。

## 7. 对 d-token 的直接建议

- 保留六页 IA，不增加大量一级菜单。
- 在连接工作台增加“选择 Agent → 选择上游 → 审查 → 应用 → 验证”的明确步骤条。
- Overview 只展示四到六个关键状态，详细证据通过抽屉或二级页面展开。
- Doctor 不只显示检查结果，还要给出安全修复动作和预计影响。
- Changes 页面成为所有写操作的统一审计入口。
- Settings 增加 updater、托盘、单实例、启动时运行和数据保留策略，但保持默认保守。
- 任何 Optical active 设置必须置于高级区域，默认关闭，并显示缺失的发布门槛。
